## ADDED Requirements

### Requirement: 工作树冲突纳入开工检查

开工检查 SHALL 判定「同一分支被两个及以上工作树同时签出」这一状态，与既有检查项在同一处
输出结论，并共同决定开工放行与否。

该结论 MUST 追加在既有检查项之后，不得插入既有项之间——既有项的顺序与名称是输出契约的组成部分。

#### Scenario: 存在工作树冲突

- **WHEN** 工作区存在同一分支被多个工作树签出的状态
- **THEN** 该项判定为不通过
- **AND** 开工检查总结论为不通过、命令退出码非零
- **AND** 结论文本点名冲突分支及其涉及的工作树数量

#### Scenario: 不存在工作树冲突

- **WHEN** 各工作树签出的分支互不相同（含 detached HEAD 的工作树）
- **THEN** 该项判定为通过
- **AND** 结论文本给出参与统计的工作树数量

#### Scenario: 无法判定

- **WHEN** 工作区不是 git 仓库，或 git 不可用导致查询失败
- **THEN** 该项不得据此判定为不通过
- **AND** 结论文本 MUST 显式说明「无法判定」及其原因，使该结论可被解释而非静默通过
- **AND** 开工检查本身 MUST NOT 因查询失败而抛出异常

### Requirement: 新检查项不影响既有项的结论

新增该检查项 SHALL NOT 改变既有任何检查项的判定结果。既有项的通过与否只由各自原本的依据决定。

#### Scenario: 冲突只影响自身

- **WHEN** 在同一工作区先后以「无冲突」与「存在冲突」两种状态执行开工检查
- **THEN** 除本项外，其余各项的通过与否在两次之间完全相同
- **AND** 总结论由全部检查项共同决定（任一项不通过则总不通过）

### Requirement: 开工检查的冲突判定不做分级

开工检查 SHALL 对工作树冲突只给出通过 / 不通过，MUST NOT 读取并发门禁的分级配置
（`concurrentGuard.worktreeCollisionSeverity`）来调整自身结论。

理由：两个接入点分工不同——并发门禁负责分级与降级，开工检查只回答事实层面的「有没有冲突」。
让一个接入点的旋钮悄悄改变另一个的判定，会让「preflight 过了」这句话的含义变得不可预期。

#### Scenario: 并发门禁被降级时开工检查仍拦

- **WHEN** 并发门禁配置把工作树冲突降级为软警告，且工作区确实存在冲突
- **THEN** 开工检查在该项上仍判定为不通过
