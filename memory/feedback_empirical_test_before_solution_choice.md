description: 用户要求「先做链接可行性实测，再定软链还是生成方案」；涉及技术选型时先跑实测拿到退出码/行为级真证，再给判定与方案
type: feedback
from: Agent
---

当用户抛出一个**技术方案选型问题**（例如「软链还是生成脚本」），不要先在文字上论证哪种方案更优雅，也不要直接开始实现；应**先做一轮可行性实测**，用可复现的命令与退出码/行为结果作为判定依据，再给方案结论。

**Why**: 2026-10-22 双 Agent 配置同步任务中，用户直接下达指令「先做『链接可行性实测』，再定软链还是生成方案」。我若凭直觉选软链，会完全错过三个致命事实：治理门禁脚本对 symlink 版 `AGENTS.md` 退出码 1（内容按整行纯路径校验，不解析 inode）、Claude Code `import` 根本没有 codearts source、CodeArts 记忆路径在配置中固定不可改。实测把这三条全部证伪，直接推翻「软链为主」的默认思路，改判为「全部走生成」。

**How to apply**:
- 触发条件：用户在请求中点名某种手段/方案（软链、生成脚本、共享目录、API 对接等）并要求据此决策。
- 正确形态：先列出「本会话可证 / 需重启后才可证」两类实测项，逐条给出命令与结果表格，然后写「方案判定表（目标 ↔ 判定 ↔ 依据）」，最后声明口径（核验日、分支、分母、版本、依据命令）。
- 不可证的项要显式列为「待重启验证 V1/V2/V3」，不要混进结论里当既成事实。
- 结论后接「下一步建议做什么」并征询确认，而不是直接开干。
