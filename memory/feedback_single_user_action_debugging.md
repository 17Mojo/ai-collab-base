当用户回「还是没有出现 X」时：**不要**继续盲改代码，**也不要**反复要求用户回报中间过程日志。把排查收敛成三步：**先做一次可判定的二分判定 → 穷尽 Agent 侧可自行核验的环节 → 只把不可替代的那一个人证动作留给用户，并给出明确成功标志。**

形态要求：列出互斥分支，让用户**只回答属于哪一支**（如「有 initialized 但报 No adapter」 vs 「连 initialized 都没有」）；每轮只留一个待回答项，不一次抛多个问题；能用构建产物/清单/日志字符串自证的假设一律自己验。

**Why:** 2026-11-02 千问适配器日志排查中，连续多轮要求用户回报 Console 日志、且在用户反问「你自己不能在 chrome 浏览器上操作吗？」之后，才转向先确认 Agent 侧能力边界（内置 browser 不可用、9222 非可用 DevTools 接口）并改用二分判定。用户偏好「先核对真证」与「直接可执行的操作指导」，对来回追问日志的循环容忍度低。

**How to apply:**
- 改代码前先自问：这个假设能否自己验证？能就别推给用户。
- 给用户的指令要含**可复制动作 + 判定标准**（看哪一行日志、进哪个入口），对齐其「明确访问地址、页面入口、逐步点击」的偏好。
- 当 Agent 确实做不到（浏览器不可读、无法加载扩展）时，**先声明边界再给替代路径**，不要含糊成「我去看一下」。
- 参见 `project_real_chrome_verification.md`（真机验证的能力边界）。
