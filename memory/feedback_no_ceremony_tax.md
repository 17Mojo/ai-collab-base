交付报告与 closeout 摘要**不得列举流程遵循情况**（哪个 Skill 被触发、门禁逐项执行表、"我遵守了我自己定的流程"）。closeout 摘要只保留 5 行：改了什么 / 测试结果 / 还有什么没做 / 风险 / 回滚方式。门禁从"每次 closeout 全跑"改为**分层触发**：每次提交只跑机械秒级项（测试全绿、契约校验、RESULT 时间戳格式）；每周跑状态漂移、ACK 覆盖、覆盖率与 mypy 趋势；每两周或里程碑跑全量 closeout + 健康度评估 + 事实快照。

**Why:** 2026-10-22 审计指出项目存在至少 5 层嵌套的过程产物（wave-closeout → ack-gatekeeper → state-drift-detector → timestamp-enforcer → session-handoff，叠加每任务强制 1 个 RESULT 文件 + 强制 acceptance_commands）。单个门禁都合理，但它们对同一件事反复检查，且**失败时的默认动作是"再写一份报告"而不是"改掉问题"**。报告里的 Skill 合规性表格对使用者零价值，对改进也接近零价值，还会反向激励"把流程写漂亮"而非"把问题修掉"。

**How to apply:**
- 写 RESULT / closeout / 开发日志摘要时，只写结果与风险，不写"走了哪些流程"
- 门禁失败时先修问题，不要靠补报告交差
- Skill 的正确用法是"防错"，不是"写报告"
- 设计新门禁时先问"这条检查对应哪个真实用户可见缺陷"，否则降级为趋势观察或删掉
- 同源"别做"清单：不再写"项目全貌说明"类手写文档（改用自动生成事实快照）；不用文档标注 P2/P3 代替删除或归档（半死文件比不存在更危险）；不在覆盖率上追数字（覆盖率只当信号："这段新代码没人测，去看是不是真没测"）；不同时推进多条产品线；不把"多 Agent"当目的本身（1–2 个 Agent 的真实场景下，编排复杂度有一部分是过度设计）
