## 场景 A：用户已给出明确目标 → 反推应做项清单

当用户在请求里**已经明确了目标**（例如「配置信息一致 + 链接 + 实时同步」），回答应直接给出**从该目标反推出来的应做项清单**，并标注每项「对应哪个目标 / 真证依据 / 优先级」；**不要**把结论包装成若干并列的可选项让用户自己挑。

**Why:** 2026-10-22 双 Agent 配置核查中，我给出的是「1/2/3 三个可选方向 + 需要我进一步做哪一项」，用户随即反问「根据我提出的目标应该做哪些项」——并列可选项没有回答用户真正的问题。用户要的是「目标已定，请给出达成它所需的完整清单与优先级」，选项化回答把判断责任又推回给了用户。

**How to apply:**
- 触发条件：用户请求里含明确的成功标准、关键词约束或多目标并列。
- 正确形态：目标逐条 → 应做项 → 依据（真证/文件/命令）→ 优先级（P0/P1）；并区分「硬需求」与「连带收益」。
- 仍需保留「待验证点 / 不可裸承诺」段落，但放在应做项之后作为风险提示，而非用来替代清单。
- 同类场景（收口计划、待办拆解、回归清单）一并适用：目标明确时不要问「你想先做哪个」。

## 场景 B：用户问「具备动手条件了吗／还需更多实测吗」 → 按线就绪度判定

此时**不要**回答一个全局的「可以 / 还不行」。把待办**按工作线拆分**，逐线给就绪判定（✅ 可动手 / ❌ 差哪几项），对每个欠项标明**类型**（实测 / 口径确认 / 现场核对）与**阻塞谁**，最后以「二选一」请用户授权推进顺序。

**Why:** 2026-10-22 双 Agent 配置同步任务，用户在我给出实测结论后追问就绪度。真实情况是「规则线已闭环、记忆线还差 1 项实测 + 1 项口径」；若只回「还不能动手」会白白阻塞可立即推进的部分，若只回「可以动手」则在记忆线方案形态（单向镜像 vs 双向）上押注未拍板的前提。

**How to apply:**
- 判定前先补现场证据：分支是否被其他进程切换、与 `origin/main` 的差异、是否已有同主题产物或实现（避免重复劳动）。
- 已证可行且无阻塞项的线要**明确授权立即推进**，不要与未就绪的线打包等。
- 沙箱内取不到真证的实测要显式标为「需非沙箱重跑」，并给出可直接复制执行的命令与**可判定的成功标志**（如命中特定 token），不要含糊成「待验证」。
- 口径类决策（如同步方向）标为「需你拍板」，不要替用户默认。

## 场景 A 与 B 的边界（消歧）

「二选一授权」只适用于**就绪度 / 推进顺序尚未拍板**的场景（场景 B）；一旦用户已把目标或成功标准说清（场景 A），再给「你选 1/2/3」就是把判断责任推回用户，违反场景 A。判断依据是**用户请求里有没有明确成功标准**，而不是话题是否相似。
