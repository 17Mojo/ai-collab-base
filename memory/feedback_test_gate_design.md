设计测试门禁时需分层：硬门禁（阻塞性）只放产品现状真实可达的基线项，软警告（告警/信息）承载理想规范类特性。**测试不应通过造假或为通过门禁而反向改造产品代码来过关**。

**Why:** 在 `tests/e2e/test_ui_accessibility.py` 重写时发现，`popup.html` 实际只有 3 个 `<div>` + `#studio-panel`，完全没有 `<main>/<section>/<header>` 等语义标签。若把 `has_semantic_landmarks` 设为硬门禁，它在当前 popup.html 上**永远过不去**。两条路：(a) 改造产品代码仅为通过测试 —— 侵入式且失真；(b) 假阳性通过 —— 欺骗门禁、掩盖问题。用户选择了第三条路：**分层对齐产品现状** —— 硬门禁只留无障碍基线（lang/UTF-8/viewport/title/对比度/可点击尺寸/disabled 处理），"语义标签"降级为告警信息、不阻断门禁。

**How to apply:**
- 设计任何门禁（lint / test / CI check）前，先 `grep`/`Read` 摸底真实代码结构，再决定哪些是硬门禁、哪些是软警告
- 硬门禁三原则：(1) 必须是产品现状已支持的；(2) 失败必须对应真实缺陷而非缺失理想特性；(3) 通过率应在当前代码上就能达到
- 凡是"应当有但当前没有"的特性 → 软警告 + 工单，不阻断门禁
- 反模式警示：不要为让测试通过而改产品代码（除非产品本身就是缺陷）；不要让测试假阳性通过（默默 skip / 弱化断言）
- 适用于：可访问性测试、代码规范检查、安全扫描、覆盖率门槛等所有门禁场景
