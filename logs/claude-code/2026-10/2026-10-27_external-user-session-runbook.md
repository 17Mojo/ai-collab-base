## 关键判断

- **手册是给主持人的，给试用者的只有 `EXTERNAL_USER_ONBOARDING.md`**。
  手册里写着「不代劳」「不提示」这类内部约定——给试用者看就等于告诉他
  我们在测什么，证据当场作废。
- **D0–D7 是「盯着症状看，但不告诉他」**。6 个已修断点各自对应一个
  **外部可见症状**（「框里有字但按钮是灰的」）。主持人一旦说破，
  这次证据就废了——所以观察清单和红线是配套的。
- **L2 观测器不注入、不点发送**，发送由试用者本人做。这是「探针永不发送」
  红线的唯一合法例外形式：**发送是人做的**，机器只记录时间线。
- **L2 登记必须用已存在的 run**（`RMR-2026-10-26-01`）——另起一份新 run
  只登记 L2 的话，`verify` 会报「平台 X 缺 L1 记录」。
- **`verify` 退出码 2 在「一场只覆盖一个平台」时是正常的**（一致但没跑完），
  手册写明了，免得主持人把它当成失败。

## 附带：修一个真缺陷，顺带翻出 5 条存量违规

`scripts/verify_task_file_contracts.py` 的通配符写成 `TASK_*.md`（下划线），
而本仓工单文件名是 `TASK-P1-…-001.md`（连字符）⇒ 不带参数跑时它**一个工单都找不到**，
打印「没找到工单文件」就退出。这个 bug 此前不可见，因为脚本只被显式传
`--task-id` 用过，而那条路径绕开了它。

修好之后脚本从「扫到 0 个」变成「扫到 23 个」，于是翻出 5 条
**与本工单无关、此前从未被机器验过**的存量违规：

| # | 工单 | 违规 |
|---|---|---|
| 1 | `TASK-P1-DISPATCH-MODEL-FALLBACK-001` | `change_id: feature/no-spec` 不在白名单 |
| 2 | `TASK-P0-CONSENSUS-ENGINE-001` | `change_id` 字段整个缺失 |
| 3 | `TASK-P1-PREFIX-DERIVATION-001` | 缺 `primary_skill`、空 `support_skills` |
| 4 | `TASK-P1-PREFIX-DISJOINT-001` | 同上 |
| 5 | `RESULT-PREFIX-DISJOINTNESS-2026-10-23.md` | 缺工单 `acceptance_commands[0]`（**合并写法**）的逐字命中 |

5 条全部**补齐并留痕**，取值全部来自仓内既有证据（结果文件 §0、
工单正文收口说明、同族工单写法），不是猜的。补齐后门禁绿：
`checked=23 invalid=0` / `audited=23 consistent=23` / 退出码 0。

**没有把门禁放宽，也没有跳过任何一条。**

### 一个容易误判的点

`update_task_contract` 的 `_set_str` / `_set_list` **跳过 None 与空值**。
所以「工单文件里某字段是空的」这件事，**从状态库那侧永远修不好**——
脚本从文件推送，空值等于没推。唯一的修法是**改工单文件本身**。

第 1 条就是活例子：当年是用 CLI 把状态库里的 `change_id` 改成了
`bugfix/no-spec`（结果文件 §0 有留痕），**但工单文件本身没跟着改**——
校验脚本按文件读，于是把非法值又推了回去。

### 顺带修正一处无出处的数字

`RESULT-PREFIX-DISJOINTNESS-2026-10-23.md` 原写「前缀相关用例 **54 passed**」，
实际是 **45 passed**。逐 commit 复验（检出 `e88e1c8` / `5b9160e` / `2f72286` /
`4af0efd` / `61afa3f` 逐个跑同一条命令）⇒ 分别是 38 / 45 / 45 / 45 / 45，
**54 在任何一个 commit 上都没出现过**。按实测值更正并留痕。
