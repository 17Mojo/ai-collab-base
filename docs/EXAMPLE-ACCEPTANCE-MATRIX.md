# 应用范例验收矩阵 —— 「跑通」的单一事实源

> 建立日期：2026-11-18
> 适用对象：`docs/APPLICATION-EXAMPLES.md` 的范例一 ~ 范例四（范例五/六不在本表范围，理由见 §6）
> 唯一目的：让「范例 X 跑通了没有」这句话有**可复核的答案**，而不是一份措辞含糊的总结表。

---

## 0. 为什么需要这张表

`APPLICATION-EXAMPLES.md` 结尾的「六大范例 × 实测判档」表，判档列写的是：

| 范例 | 判档原文 |
|---|---|
| 多平台共创 | 「幂等/策略链成立」 |
| 多 Agent 开发 | 「看门狗/审计/补票成立」 |
| 深度研究 | 「fallback 与跨源验证成立」 |

这些措辞描述的是**组件各自成立**，不是**整条链路跑通**。两者差距很大：

- 「看门狗成立」= `ack_watchdog.py` 的函数有单测、能算出候选集；
- 「ACK 闭环跑通」= 真的注册了任务 → 真的派发了 → 真的 ACK 了 → 真的产出了回执 → 看门狗和一致性审计在那个回执上给出判定。

前者全绿而后者一次没发生，完全可能——本仓已有先例（N36 的 `MultiPlatformExecutor`，
文件在、符号在、单测在、**零生产入口**；N31 的 Hook 脚本同类）。

所以本表要做的第一件事，是把「跑通」拆成四档，不再用二值判断。

---

## 1. 「跑通」的四档定义

| 档 | 名称 | 成立条件 | 判据强度 |
|---|---|---|---|
| **D0** | 条件不备 | 判据所需的前提在磁盘/环境上就不存在 | 无法验收，不是缺陷 |
| **D1** | 组件级 | 单个模块有单测证明其行为，但**没有任何真实调用链**把它串起来 | 弱：证明「零件好」，不证明「机器能转」 |
| **D2** | 链路级 | 用真实命令/真实请求把多个组件串起来跑通一次，有**散落的**留痕（日志行、单个 JSON） | 中：证明「转起来过」，不证明「按文档步骤转」 |
| **D3** | 端到端留回执 | 按文档描述的**完整步骤**从第一步走到判据终点，产出**带时间戳、可被他人复核复现的回执文件** | 强：本表认可的最高档 |

**只有 D3 才能对用户说「这个范例跑通了」。** D1/D2 只能说「零件成立」「链路曾转起来」。

这条纪律的代价是诚实：按此口径，截至 2026-11-18，**范例一（白名单 5 站内）与范例三达到 D3**，
范例二停留在 D1+D2，范例四为 D0。

### 2.1 关于范例一的「全量」

11 个 adapter 中，除白名单 5 站外的 6 站各有**不同性质**的阻塞，不能统一说「还没测」：

| 平台 | 状态 | 性质 | 依据 |
|---|---|---|---|
| qianwen | 用户裁定移出白名单 | **政策** | `platform-freeze.mjs:7-9`（有防范非人类操作机制，2026-11-18 改判换成 stepfun） |
| deepseek | 冻结 A/B 样本 | **政策** | `platform-freeze.mjs:52` `FROZEN_AB_PLATFORMS` |
| longcat | 冻结 A/B 样本 | **政策** | 同上 |
| ChatGPT | `bot_check` HTTP 403 | **平台侧不可控** | `RESULT-REAL-MACHINE-REACHABILITY-2026-10-26.md:68` |
| Claude.ai | `bot_check` HTTP 403 + 「安全验证」 | **平台侧不可控** | 同上 `:69` |
| gemini | 不在白名单，无近期真机记录 | **未排期** | `platform-freeze.mjs` 未提及；仅在历史 `fiveSites` 名单中出现 |

**结论**：把「范例一全量跑通」理解成「11 站全绿」是**不可达**的——其中 2 站是平台侧 403，
不是本项目能解的。可行的口径只有两种，**必须由用户选定一种**，否则这句话永远无法结案：

- 口径 A（窄）：「全量」= 白名单 5 站 ⇒ **已达成 D3**，无需再跑；
- 口径 B（宽）：「全量」= 白名单 5 站 + 用户可提供登录态的站（如 chatgpt/claude 登录后可能绕开 403）⇒ 需用户配合扫码/登录。

## 4. 口径纪律（读本表前必看）

1. **D3 是机器判定，不是人工验收。** `success:true` 只证明「链路跑通且产出非空」，
   不代表内容质量合格、不代表产品验收通过（该声明原见 `RESULT-L2-ACTIVE5-NOV18` §4，此处继承）。
2. **「点按实测」这把尺子只量得动范例一和范例二。** 范例三是 CLI + 状态机协议，
   范例四是后端 + MCP 集成，二者**没有浏览器点按对象**（`agent_orchestrator.py`、
   `ack_protocol.py` 对 `playwright/chromium/page.` 的引用数均为 0）。用「点按」要求范例三/四，
   等于用尺子量温度——永远量不出结果，还会把「没测过」误判成「测不过」。
3. **档位可升不可跳。** 从 D1 直接宣布 D3 必须有端到端回执佐证；
   任何「因为 A、B、C 都成立，所以整条链路成立」的推理，在本表里不算证据。
4. **卡点是分性质的**：政策（用户可改）、平台侧（不可控）、未排期（可排）、
   设计使然（不是缺陷）。混为一谈会导致「永远修不完」。
