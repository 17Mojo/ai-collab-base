### 1.5 复核记录（2026-11-03 10:40）——上一节的结论需要修正

`_buildPrompt` 那 1 行确实改对了，但**只修它不够**。复跑真机调用形态后，暴露的是三个独立缺陷。

**先认一个自己的错**：上一轮 `probe-full.mjs` 得到「0/6 残留」是**探针自己造的假象**。该脚本第 27 行手动写了 `execution.output[step.output_field] = r.output`——而这正是引擎在顺序路径上**没有**做的事。探针替引擎补了这一步，于是掩盖了真缺陷。教训：探针必须走引擎的真实入口（`execute()`），不能自己拼装引擎内部的收尾动作。

#### 四象限对照（全部走 `execute()` 真入口）

| # | 引擎 | 传参 | 残留提示词 |
|---|---|---|---|
| ① | 现状 | popup 真实形态（`message.input === undefined`） | **6/6** |
| ② | 现状 | 手动传 `topic` | **4/6** |
| ③ | 补回写 | popup 真实形态 | **3/6** |
| ④ | 补回写 | 手动传 `topic` | **0/6** |

两组变量各自独立生效，缺一不可 ⇒ 修一个不够。

#### 缺陷 D2：顺序执行路径不回写 `execution.output`（本轮新发现，未修）

`pack-executor.js` 里 `execution.output[...]` 全库**只有一处写入**：

| 位置 | 所在函数 | 是否覆盖顺序路径 |
|---|---|---|
| `:450` | `_executeWorkflowWithBranching` | ❌ 仅分支路径 |
| `:386-393` | 顺序路径（`hasBranches === false`） | ❌ **完全没有回写** |

`xiaohongshu_knowledge_creator.json` 8 步、0 个 `branches` ⇒ 必然走顺序路径 ⇒ `execution.output` 全程为空 ⇒ 下游只能拿到外部 `input`。

后果比 `_buildPrompt` 更严重：**这是「包内上下文传递」整体失效，与用户传不传参无关。**

修复（3 行，与分支路径对齐）：

```js
for (const step of steps) {
  const stepResult = await this._executeStep(step, execution);
  execution.steps.push(stepResult);
  if (stepResult.output) {                                    // ← 新增
    execution.output[step.output_field || step.id] = stepResult.output;
  }
  if (!stepResult.success) { ... }
}
```

已在 `/tmp/pe-patched.js` 打补丁验证：单独加这 3 行，②→④（4/6→0/6），确认是本缺陷。

#### 缺陷 D3：`{{topic}}` 在真机形态下无来源（验收③的直接否决项）

| 环节 | 位置 | 事实 |
|---|---|---|
| popup 发送 | `public/popup.js:89-93` | 只发 `{type, packId, tabId}`，**无 `input` 字段** |
| 后台转发 | `service-worker.js:156-161` | `packExecutor.execute(message.packId, message.input, {...})`，`message.input` 为 `undefined` |
| 引擎兜底 | `pack-executor.js:339` | `input = {}`（默认值命中）⇒ `execution.input === {}` |
| local 步骤 | `pack-executor.js:625-631` | 只做 `input[field] \|\| output[field]` 取值，**不校验** `config.required_fields` |

全库 `EXECUTE_PACK` 只有 2 个出现点（上面两处），**没有任何 UI 收集 Pack 输入**；Python CLI 也没有 pack 输入入口（`_cli_main.py:965` 的 `--input` 属 `activate` 命令，无关）。

补充证据：`required_fields` 在 JS 侧**零引用**，所以缺失输入不会报错，只会静默产出 `{topic: undefined}`。

占位符来源对齐（`pack` 内 7 个变量）：

| 占位符 | 出现次数 | 来源 |
|---|---|---|
| `topic` | 3 | ★ 仅外部输入，**无产出步骤** |
| `hook_statement` / `explanation_text` / `use_cases` / `takeaway_content` / `visual_content` / `boundary_notes` | 3/3/2/2/1/1 | 步骤产出（受 D2 阻断） |

而 `topic_info`（step_1 产出）**没有任何提示词消费** ⇒ step_1 目前是纯装饰步骤，只起到「声明 topic 属于输入」的文档作用。

#### 缺陷 D4：`step_5_boundary` 步骤类型用错，产出 `[object Object]`

`step_5_boundary` 被声明为 `local`，`output_field: boundary_notes`，`input_fields: ['topic_info']`。`_executeLocalStep` 原样返回 `{topic_info: {...}}` ⇒ `execution.output.boundary_notes` 是个对象 ⇒ ④ 里实测渲染成 `边界：[object Object]`。

两处错：

1. **包侧**：该步 `config.required_elements` 是「明确什么人适合/不适合」这类**语义生成要求**，local 步骤永远做不到，应为 `generation`；
2. **引擎侧**：`_executeLocalStep` 是无变换的直通，且返回值按**输入字段名**建键（`topic_info`）而非输出字段名（`boundary_notes`），形状也不对。

### 2.1 三步改动（合计约 9 行）

| # | 改动 | 位置 | 行数 |
|---|---|---|---|
| a | 入参归一化：`StepType(step["type"].lower())` | `schema_v2.py:723` | 1 |

| d | `ai` 收编为第 7 种类型（Enum + 白名单） | `schema_v2.py:31` / `schema_validator.py:103` | 2 |

### 2.2 为什么是「Chrome 补 5 个 case」而不是「Schema 砍掉 5 种」

Chrome 的 `_executeAIStep` **只有一条执行路径**（`_buildPrompt` → `SEND_TO_AI`），它压根不区分 analysis/generation/fusion——因为没有第二套执行机制可用。让 Chrome 真的实现 5 种不同行为，是没有需求的伪实现。

所以正确方向是：**Chrome 侧把它们统一当「调 AI」处理，语义差异留在 Python 侧**。这既符合 Chrome 的真实能力，又不动 Python 已有的 5 个 `_execute_*` 实现。

- ✅ `external-user-smoke.json` 的 `validate_pack` 通过（不再报 `Invalid step type: ai`）
